# ADR-005: 宣告式型別註冊表 + 核心固定、可擴充的關聯詞彙

## 狀態(Status)

accepted

## 背景(Context)

Entity 的型別(角色片段、歷史片段、道具、對話、劇情片段……)與關聯的種類(取代、矛盾、
牽涉、發生於……)都是會**隨著使用長出來**的東西。寫故事的過程中一定會冒出當初沒想到的
片段種類與關係。

design-studio 在這件事上有一個被驗證過的答案:內容層是純資料宣告(`ModuleSpec`),引擎層
完全不認識任何具體模組。新增一個設計模組只要加一個檔案並在註冊表加一行,網頁選單、CLI 選項、
目錄結構、資源庫分組全部自動跟進——8 個模組實際驗證過,引擎/伺服器/前端一行沒改。

但關聯不同於型別:衝突偵測與圖遍歷需要**知道某些關聯的語意**才能推論。「A supersedes B」
必須讓引擎知道 B 已過時;「師承於」則不需要引擎懂任何事。

## 決策(Decision)

### 型別:完全宣告式,core 不硬編任何型別

每個 Entity 型別是 `types/` 底下一份 TOML 宣告,內容包含:

- `key` / `name`——鍵與人類可讀名稱
- `fields`——該型別建議填寫的 Meta 欄位與提示(引導作者與 AI 該寫什麼)
- `allowed_links`——該型別合理的關聯種類(用於檢查與 AI 的提示)
- `stages`——階段式工作坊的階段清單(S5 才用到,先宣告不影響 S1–S4)

`storyflow-core` 只看到 `EntityType` 這個抽象(實質是字串 + 註冊表查詢),不認識
`character-fragment` 是什麼。新增型別 = 加一份 TOML,`core` / `service` / `server` / `cli`
全部不改。

### 關聯:核心詞彙固定,其餘自由

引擎認得八個核心關聯並據以推論:`contradicts` / `supersedes` / `derivedFrom` / `partOf` /
`involves` / `occursIn` / `references` / `convergesTo`。所有關聯都**有方向性**,存在來源端。

其餘關聯可用任意字串(「師承於」「宿敵」「前身是」)。引擎把它們當純標註儲存,可查詢、
可顯示、可被 AI 讀到,但**不驅動任何邏輯**。

型別在 `LinkKind` 上表達為「封閉建構子 + 一個 `Custom Text`」,因此對核心關聯的處理可以做
窮盡比對,編譯器會在新增核心關聯時指出所有需要更新的地方。

## 考慮過的替代方案(Alternatives Considered)

**型別**

- **固定封閉 enum**:編譯期完全型別安全、窮盡比對全面。但新增一種片段就要改程式重新編譯——
  而寫故事時「我需要一種新的片段」是常態,不是例外。
- **完全自由字串 + tag**:最自由,但沒有任何欄位引導。AI Agent 建立片段時不知道這個型別
  該寫哪些欄位,產出品質會很不穩定;也無法檢查關聯是否合理。

**關聯**

- **完全固定詞彙表**:推論最可靠。但寫故事時想表達的關係裝不下,使用者只好硬塞到最接近的
  核心關聯裡,反而汙染了推論的輸入。
- **完全自由字串**:最有彈性,但衝突偵測就沒有結構層可用,只剩 FTS + LLM 兩層——而結構層是
  三層裡唯一確定性、可重現、零成本的一層,放棄它代價太大。

## 影響(Consequences)

**正面**

- 新增 Entity 型別的成本降到「寫一份 TOML」,不需要開發者介入
- 衝突偵測的結構層有可靠的語意輸入,`contradicts` / `supersedes` 的推論是確定性的
- `allowed_links` 與 `fields` 同時是給 AI Agent 的提示來源——API 可以直接把型別宣告餵給
  claude code,讓它知道建立這種片段該填什麼
- 核心關聯是封閉建構子,未來新增一個核心關聯時編譯器會列出所有待處理的地方

**負面 / 成本**

- 型別宣告是執行期載入的資料,寫錯(欄位名拼錯、關聯名不存在)只能在載入時檢查並報錯,
  不是編譯期。因此 S1 就要做型別宣告的驗證與清楚的錯誤訊息
- 自訂關聯不驅動邏輯,使用者可能誤以為「我寫了『矛盾於』引擎就會偵測」——CLI 與 API 在遇到
  自訂關聯時應提示對應的核心關聯
- `types/` 隨程式碼版控(不隨 Vault),因此各 Vault 共用同一組型別。若未來需要 Vault 專屬型別,
  再擴充成「程式碼內建 + Vault 覆蓋」兩層
