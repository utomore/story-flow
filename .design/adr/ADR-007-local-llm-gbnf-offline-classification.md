# ADR-007: 本機 LLM 離線分類寫入索引,查詢時不呼叫 LLM,輸出受 GBNF 文法約束

## 狀態(Status)

Accepted。實作於 `ai/` 套件,已對真實素材庫執行(叢集層分類 8 分鐘零失敗、逐份視覺標註
約 8 小時批次)。

## 背景(Context)

素材庫裡商業素材包的檔名、包名、作者全是英文,中日韓全文索引機制本身沒問題(能搜到
中文命名的參考包),缺的是**中文語意標籤**——語料裡沒有中文字,任何中文查詢都是零筆。

工作室是離線本機環境,沒有雲端 LLM API 的預算或延遲要求,但有一台可跑 llama.cpp 的機器。

## 決策(Decision)

- **本機 llama.cpp,OpenAI 相容端點**,設定值 `lcBaseUrl`/`lcModel` 皆可用 CLI 旗標覆寫
  (`--llm-url`/`--llm-model`),不是寫死。推論服務沒開時所有指令優雅退出,不弄壞資料庫、
  不讓伺服器掛掉。
- **離線批次寫入,不在查詢路徑呼叫 LLM**。分類/標註結果寫進 `ai_suggestions` 暫存表待
  人工確認,確認後 `apply` 寫回索引並觸發 `reindexFts`。之後中文搜尋是純 SQLite 查詢:
  零延遲、零 LLM、推論服務關掉也照常運作。`assetdb ai query` 是額外的自然語句入口,
  不是主要搜尋路徑。
- **輸出用 GBNF 文法約束**:JSON Schema 編譯成 GBNF,模型物理上吐不出詞彙表外的分類值,
  判斷不出來時填 `unknown`,不是靠 prompt 說服模型守規矩。
- **失敗語意分兩層**:`StepFailed`(這一筆有問題,記錄後續跑)vs `StepAbort`(推論服務掛了,
  整批停下、佇列保留為 `pending`)。若把服務中斷當成逐筆失敗,幾千筆待處理項目會被錯誤
  標記,工作佇列會被破壞 —— 已驗證:指向死掉的 port 跑三筆,結果是 0 筆被標成失敗。
- **LLM 呼叫嚴格在資料庫交易之外**:單次呼叫可能耗時 5.8 秒,遠超過 `busy_timeout=5000`,
  跨交易持有寫鎖會讓同時運行的伺服器寫入失敗。每筆的建議與狀態在自己的交易內提交,
  資料庫本身就是斷點續跑的檢查點。
- **標籤一律 `source='inferred'` + `INSERT OR IGNORE`**,不覆蓋既有資料;人工標籤
  (`manual`)永遠優先,重跑批次不會覆蓋人工決策。
- **thinking 模式預設關閉**:是否能關閉推理段落取決於模型的 chat template,實測兩顆
  模型結果相反(一顆無效只能靠加大 `max_tokens`,另一顆關閉後 4.8s→0.2s 且品質更好)。
  預設關閉對支援的模型是巨大加速,對不支援的模型只是被忽略的欄位,無副作用。

## 考慮過的替代方案(Alternatives Considered)

- **雲端 LLM API**:離線本機環境,且一次性批次分類(約 6 千筆)用雲端 API 的成本與延遲
  不划算,已放棄。
- **查詢時即時呼叫 LLM 做語意搜尋**:會讓每次搜尋都依賴推論服務在線,且延遲遠高於
  SQLite 查詢,已放棄,改為離線寫入 + 純 SQLite 查詢。
- **開放式生成標籤(非 GBNF 約束)**:曾評估自由文字生成,但分類需要落在封閉詞彙表
  才能被 facet 篩選機制使用,已改為 GBNF 約束輸出。

## 影響(Consequences)

- 分類品質與覆蓋率取決於一次性批次執行的完整度;5,315 份內容產生約六萬筆建議,
  無法逐筆人工審查,實際做法是抽樣檢查後整批確認(信心值缺乏鑑別力,`--min-confidence`
  目前無效,模型幾乎全部回報 0.9–1.0)。
- `apply --confirm` 綁定自動 `reindexFts` 是刻意設計,避免「確認建議但忘記重建索引,
  中文搜尋仍零筆」這個最容易靜默失敗的步驟被人為遺漏。
- 換模型後必須重新量測 thinking 開關與 timeout 等經驗值,這些數字不是可移植的通用常數。
