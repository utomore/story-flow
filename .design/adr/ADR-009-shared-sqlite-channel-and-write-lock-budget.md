# ADR-009: 共用 SQLite 檔是正式的行程間通道,寫交易的持有時間必須以毫秒計

## 狀態(Status)

Accepted(2026-08-21)。由 `/arch-audit system` 的全域檢測促成:檢測發現既有的規則措辭
存在漏洞,而漏洞的根因是這條通道從未被寫進通訊拓撲。

## 背景(Context)

系統交付兩個獨立執行檔:`assetdb`(CLI,跑掃描、叢集、AI 標註等長時間批次)與
`assetdb-server`(常駐,提供查詢與縮圖)。**兩者之間沒有任何直接通訊** —— 沒有 IPC、
沒有訊號、沒有共用記憶體。它們唯一的交會點是同一個 `.assetdb/assetdb.sqlite` 檔案。

這個事實一直存在,但**從來沒有被寫進「通訊拓撲與原則」**。拓撲只定義了三種通道:
同進程函式呼叫、HTTP/JSON、外部 sidecar。共用檔案這條被漏掉了。

漏掉的後果不只是文件不完整。全域錯誤處理策略原本的第 4 條寫「**長時間外部呼叫**絕不跨
資料庫交易持有寫鎖」,措辭來自 ADR-007 的 LLM 個案。而 `ingest` 的掃描把數千次檔案讀取
與 PNG 完整解碼包在單一寫交易裡 —— 那些工作既不是 LLM、也不是「外部呼叫」,**在原本的
措辭下完全合規**,實際上卻會讓寫鎖被持有數分鐘到數小時,遠超 `busy_timeout=5000`。

換句話說:規則因為缺少它所保護的那條通道的定義,措辭窄化成了個案的形狀,於是真正的
違規者從規則的縫隙走了過去。

## 決策(Decision)

**一、把共用 SQLite 檔列為第四條正式通訊通道**,與同進程呼叫、HTTP/JSON、外部 sidecar
並列,並寫明它的規則:

- **同時只能有一個寫入者**;WAL 模式下讀取者不被寫入者阻塞,反之亦然
- 取得寫鎖的等待上限是 `busy_timeout=5000`,**超過就是寫入失敗,不是排隊**
- **服務保證**:CLI 的長時間批次進行中,伺服器必須仍然可以查詢,且 CLI 自己的每一筆
  進度都要落盤(批次因此可以中斷續跑,資料庫本身就是檢查點)

**二、把寫鎖的約束改成可稽核的具體界線**,取代原本需要主觀判斷的「長時間外部呼叫」:

> 寫交易的持有時間必須以毫秒計。任何檔案讀寫、影像解碼、雜湊計算、子程序呼叫與網路
> 請求一律在交易之外完成,交易內只剩已經算好的值的寫入。

這條規則的關鍵性質是**看一眼就能判定**:交易區塊內有沒有 IO 或重運算,是可以在 code
review 與靜態檢測中機械判斷的事實,不需要爭論「這個算不算長時間」。

ADR-007 的「LLM 呼叫嚴格在資料庫交易之外」維持不變 —— 它是本條規則在 ai-tagging 的
個案,不是本條的全部範圍。

## 考慮過的替代方案(Alternatives Considered)

- **只把「外部呼叫」放寬成「長時間 IO」**:改動最小,能堵住目前這個漏洞。放棄的理由是
  「長時間」仍然需要人的判斷 —— 一次 PNG 解碼算不算?一千次呢?下一次一樣會有人認為
  自己的情況不算,漏洞會以另一個形狀重新出現。
- **規定「交易內只允許 SQL」**:規則最簡單,但會誤傷合理用法(例如交易內做一個純函數的
  小轉換),而且現有程式碼有幾處會被判違規卻實際無害,徒增雜訊。
- **調高 `busy_timeout` 或改用獨立連線**:治標。長交易本身就會讓「批次進行中仍可查詢」
  這個服務保證失效,而那是使用者實際依賴的行為(過夜跑 AI 標註時仍要能開網頁挑素材)。
- **不寫進拓撲,只在 ADR-001 的後果段提一句**:現狀就是如此,而現狀已經證明不夠 ——
  規則失去了它保護的對象,措辭就會退化成個案。

## 影響(Consequences)

- **`ingest` 的掃描目前違反本規則**,兩處:散檔掃描把整個根目錄的檔案讀取與雜湊包在
  單一交易內;壓縮檔寫入把逐筆雜湊與 PNG 解碼放在交易內。兩者需要改成「交易外算好、
  交易內分批寫入」,已列入後續的優化設計。
- 新規則是**可稽核的**,因此可以進入 `/arch-audit` 的例行檢查項目,而不是只靠人記得。
- 分批提交會讓「一次掃描 = 一個原子操作」不再成立:掃描中途失敗會留下部分寫入的索引。
  這是可接受的取捨 —— 掃描本來就設計成可重跑且冪等(壓縮檔雜湊沒變就整包跳過),而
  「跑到一半的索引」遠比「整批回滾但伺服器一小時不能寫入」好。
- 本 ADR 不改變儲存選型(ADR-001 的 SQLite 決策不變),只是把該決策一直隱含的並行約束
  提升為明確的架構規則。
