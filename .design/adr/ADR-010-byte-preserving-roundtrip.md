# ADR-010: Markdown 寫回採「未碰過的區塊逐字保留」

## 狀態(Status)

accepted

## 背景(Context)

ADR-002 讓 Markdown 成為真相來源,也因此讓**程式**與**作者**同時是這些檔案的寫入者:
作者用編輯器直接寫故事,AI Agent 透過 API 改片段的 `summary` 或補一條 `contradicts` 關聯。

問題在於,程式改一個欄位時要把整份檔案寫回去。如果寫回是「重新序列化整份文件」,那麼
作者精心排的空行、YAML 裡寫給自己看的註解、習慣的縮排風格、甚至 frontmatter 的欄位順序,
都會在 AI Agent 改一句 summary 時被靜靜地重排一次。

這在 `git diff` 上的表現是災難性的:改一個欄位,diff 顯示整份檔案都變了。作者會失去
review AI 改動的能力——而「知道某句設定是何時為何改的」正是 ADR-002 選擇 Markdown 的
第一個理由。

ADR-002 已經預告了這個成本:「必須通過 round-trip 測試(解析 → 寫回 → 再解析不失真),
否則程式寫回檔案時會破壞作者的手寫排版」。但「不失真」有三種嚴格程度,必須挑一種。

## 決策(Decision)

**採最嚴格可行的一級:未經修改的區塊逐字保留原始位元組。**

具體保證:

1. 解析後未做任何修改就寫回,結果與原檔**位元組相等**(含行尾風格、檔尾換行、
   YAML 註解、縮排、欄位順序)
2. 修改某一個片段時,**只有該片段的 ` ```meta ` 區塊**被重新序列化;檔案其餘部分逐字不動
3. 重新序列化採固定欄位順序,同一份資料每次寫出都相同

實作上的必然結果是**兩階段解析**:第一階段做無損的結構切分,`Section` 同時持有
`secHeadingRaw` / `secMetaRaw` / `secBodyRaw` 三段**原始文字切片**;第二階段才把原始文字
解讀成核心型別。寫回預設吐原始切片,只有被明確修改的區塊才走序列化路徑。

因為每一塊都是原檔的切片,位元組相等是**結構上保證的**,不是靠測試碰運氣得來的。

## 考慮過的替代方案(Alternatives Considered)

- **語意等價即可**(`parse (render (parse f)) == parse f`):`Section` 只需要
  `{ secMeta :: Meta, secBody :: Text }`,型別乾淨,實作簡單得多,而且測試好寫。
  但作者的 YAML 註解、欄位順序、空白風格會在每次程式寫入時被正規化——第一次 AI Agent
  改一個 summary,作者就會看到整份檔案的 diff,然後開始不信任這個工具。這個信任一旦失去
  就補不回來,而失去它的代價比多寫一層型別高得多。
- **全檔逐字不動**(任何修改都必須保留全檔位元組,含被修改欄位周邊的排版):最尊重作者,
  但需要一個 round-trip preserving 的 YAML 編輯器——能在保留註解與格式的前提下只改一個
  鍵的值。Haskell 生態沒有現成的(`HsYAML` 與 `yaml` 都只做 decode/encode,不做保留式編輯),
  等於要自己寫一個 YAML 子集的編輯器。S1 的工作量會翻倍,而它買到的額外價值只有
  「被修改的那個 meta 區塊裡的註解也保住」——範圍極小。
- **只讀不寫,程式永不修改檔案**(所有變更走另一個 side-car 檔):完全迴避問題。但
  AI Agent 透過 API 建立與修改片段是 S3 的核心能力,side-car 等於製造第二個真相來源,
  直接違反 ADR-002。

## 影響(Consequences)

**正面**

- AI Agent 改一個欄位,`git diff` 就只顯示那一行。作者 review AI 改動的成本降到最低,
  這是 ADR-002 選擇 Markdown 的價值真正兌現的地方
- 作者的手寫排版、YAML 註解、縮排習慣永久安全,工具不會「順手幫你整理」
- 位元組相等由結構保證,不是靠一堆 edge case 測試堆出來的
- 混合行尾(LF 與 CRLF 並存,跨平台編輯的常態)自然被保留,不需要特別處理

**負面 / 成本**

- `Section` 型別比語意等價的版本多帶三個原始文字欄位,`Document` 也要記錄行尾風格與
  檔尾換行。型別讀起來沒那麼漂亮
- 解析必須分兩階段,lexer 要精確到「這一塊從第幾個字元到第幾個字元」,不能用寬鬆的
  `lines` + `filter` 寫法
- 每個修改操作都要明確決定「重寫哪一段」;新增一種修改操作時,若忘了限制範圍,
  逐字保留的保證會默默破掉。緩解:`updateSection` 之類的編輯函式集中在
  `StoryFlow.Md.Render` 一個模組,並以「改一個欄位後逐行比對只有一行不同」的測試守住
- 被修改的那個 `meta` 區塊裡,作者原本寫的 YAML 註解仍會消失(這是與「全檔逐字不動」
  的差距)。這是明確接受的殘留成本

**中立**

- 解析方向用 `HsYAML`,序列化方向自己寫(固定欄位順序、流式 `links`)。不用 YAML 編碼器
  是這個決策的直接推論——只有被修改的節需要重寫,格式完全由我們決定,引入編碼器反而要
  對抗它的排版偏好
