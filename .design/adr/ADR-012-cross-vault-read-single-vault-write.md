# ADR-012: 讀跨全部 vault,寫只進一個 vault

## 狀態(Status)

Accepted(2026-08-23)。ADR-011 兩層狀態模型的操作語意細則。

## 背景(Context)

有了多個 vault(ADR-011)之後,每個指令都要回答一個新問題:**這次對哪些 vault 生效?**

三種可能的預設值,而且它們的風險完全不對稱:

- 查詢如果只看單一 vault,「一次找遍所有素材」這個核心用途就不存在 —— 那是專案要解決的
  第一個問題。
- 寫入如果自動跨 vault、由程式挑落點,挑錯的代價很高:`logical_name` 是**全域唯一的對外
  契約**(ADR-004),遊戲的 `Assets.hs` 常數由它產生;素材帶著授權後果,而授權設定是
  per-vault 的。
- 全部都要求顯式指定最安全,但每次查詢都要打 `--vault`,等於用人體工學換一個查詢路徑上
  根本不存在的風險 —— 查詢不改變任何狀態。

## 決策(Decision)

**一、讀跨、寫單一。**

| 類別 | 指令 | 預設涵蓋 |
|---|---|---|
| 查詢 | `search`、facet 計數、`doctor`、`tree`、`vault list` | **全部已註冊 vault** |
| 寫入 | `cluster rule` / `cluster apply`、`ai apply`、`ai suggest confirm` / `reject`、`note import`、`link` | **必須 `--vault` 指定**,程式不猜 |
| 初始化 | `scan`、`thumbs`、`index` | 不給 `--vault` 時**對每個 vault 各跑一次** |

`scan` 那一列是關鍵:對每個 vault 各跑一次,**每一次仍然只寫它自己的索引**,所以
「寫只進一個 vault」這條不變式沒有被破壞 —— 它是被重複套用,不是被放寬。

**二、查詢結果必須帶出來源 vault。** 跨 vault 的結果如果分不出哪筆來自哪裡,使用者就無法
對它採取任何行動(要 `--vault` 才能寫)。這是契約的一部分,不是呈現細節。

**三、跨 vault 讀取以 SQLite 的 `ATTACH DATABASE` 實作**,一個連線掛上多個 vault 的索引再
UNION。這之所以乾淨,是因為對外識別一律是 ULID(ADR-003):跨 vault 合併不會撞鍵。
「整數主鍵不出模組邊界」那條原本看起來只是潔癖的規則,在這裡直接付現。

已知限制:SQLite 預設的 `SQLITE_MAX_ATTACHED` 是 10。超過時的處置(分批查詢再合併,或
要求使用者縮小範圍)屬 Level 2,但**上限必須是使用者看得懂的錯誤,不是靜默截斷結果**。

**四、`--db` 保留為逃生口**:繞過中樞、直接指定單一索引,供腳本與除錯使用。日常路徑是
中樞註冊表。

**五、ADR-009 的寫鎖預算逐一適用於每個索引檔。** 伺服器可能同時 ATTACH 多個 vault,
但那些是**讀取**;CLI 的批次一次只寫一個索引。「同時只能有一個寫入者」「寫交易持有時間以
毫秒計」的規則不因為掛了多個而改變,也不需要跨 vault 的協調機制。

## 考慮過的替代方案(Alternatives Considered)

- **全部指令都要求顯式 `--vault`**:語意最單純、最安全。放棄的理由是它讓查詢也背上寫入
  才需要的紀律,而查詢不改變任何狀態;代價是永久失去「一次找遍所有素材」。
- **讀寫都跨,寫入由程式判斷落點**:人體工學最好。放棄的理由見背景 —— 全域唯一命名與授權
  後果讓猜錯的代價過高,而且它違反既有的「會改動狀態的動作預設只預覽、要人確認」精神。
- **每個 vault 開一個連線,在應用層合併**:不受 `SQLITE_MAX_ATTACHED` 限制。放棄的理由是
  排序、分頁與 facet 計數都得在應用層重做一遍 —— FTS5 的排名尤其無法在應用層正確合併,
  而全文排序正是查詢路徑的核心。超過 10 個 vault 時可以退回這條路,但不作為預設。
- **中樞維護一份跨 vault 的彙總索引**:查詢最快。放棄的理由是它讓中樞從「索引」變成
  「真相的一部分」,與 ADR-011 第一條直接衝突,而且要處理彙總與各 vault 之間的失同步。

## 影響(Consequences)

- `delivery` 的入口層改寫:資料庫路徑解析從「回傳一個路徑」變成「回傳一組 vault」,
  14 個既有指令各自表態屬於上表哪一類。
- `server` 啟動時讀中樞、ATTACH 全部 vault;前端的 facet 側欄多一個 vault 維度,
  回應 DTO 多一個來源欄位(型別產生器與漂移檢查會跟著抓)。
- `catalog` 的查詢層要能對 ATTACH 進來的多個 schema 做 UNION;FTS5 的跨庫排名是這裡最需要
  驗證的一點,應在 Level 2 就先做成可測的契約。
- 超過 10 個 vault 的處置需要一個明確的錯誤訊息;不得靜默只查前 10 個。
