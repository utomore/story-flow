# ADR-0004: Level 為嚴格樹,分支合流以 `convergesTo` 關聯表達

## 狀態(Status)

accepted

## 背景(Context)

Level 場景的結構需求是「樹狀展開、可無限增長」:根 Node 是場景本身,往下長出出場人物、鏡頭、
人物互動、對話……每一層都可以再往下接。

但真實的分支劇情幾乎一定會**合流**:玩家在對話選了強硬或退讓,兩條路最後都走到同一個結局節點。
若結構本身允許多個父節點,那它就不是樹而是 DAG。

## 決策(Decision)

**結構層維持嚴格樹**——每個 Node 恰有一個父節點(根節點除外)、不成環、同層兄弟以 `order` 排序。

**合流以關聯表達**:在分支末端的 Node 上加一條 `convergesTo` 關聯,指向要合流到的 Node。
這條關聯是註解性質的——它不改變樹的父子結構,只告訴讀者與工具「這兩條路在這裡匯合」。

```
Node A
 ├─ B ─ D  ┄convergesTo┄┐
 └─ C ─ E ───────────────┘
(實線 = 樹的父子;虛線 = convergesTo 關聯)
```

`convergesTo` 是核心關聯詞彙之一(見 ADR-0005),引擎認得它:遍歷與渲染時可選擇是否跟隨,
但**樹的走訪演算法本身永遠只看父子邊**,因此不需要防環、不需要處理多路徑。

## 考慮過的替代方案(Alternatives Considered)

- **直接做成 DAG**:更貼近分支劇本的真實形狀,合流是結構的一等公民。但所有的遍歷、渲染、
  複製子樹、刪除節點、計算「這條路徑上出場過誰」都要處理多路徑與防環,複雜度全面上升;
  而且 DAG 允許寫出無限迴圈的結構,錯誤只會在執行期爆出來。以本專案的定位(設定管理與衝突
  偵測,不是遊戲執行期的對話引擎)來說,這個複雜度買不到相稱的價值。
- **樹 + 明確的「合流節點」型別**:引入一種特殊 Node 當匯合點。等於在樹上偷渡 DAG 語意,
  兩邊的缺點都拿到了。
- **完全不支援合流**:合流的分支各自複製一份後續節點。結構最單純,但同一段後續劇情被複製多份,
  改一處要改多處——這正是 story-flow 想消滅的問題。

## 影響(Consequences)

**正面**

- 樹的合法性可由型別與少數不變量保證(單一父、`order` 唯一),不需要圖演算法
- 走訪、渲染、子樹複製、刪除都是單純的遞迴,不會有效能與正確性的意外
- 不可能寫出無限迴圈的結構
- 合流仍然被記錄下來、可查詢、可在視覺化時畫出來,資訊沒有遺失

**負面 / 成本**

- 合流是「標註」而非「結構」,因此工具不會自動保證兩條分支真的接得起來——`convergesTo` 指向
  一個不存在或不合理的 Node 時只能靠檢查指令(`story-flow level lint`)發現,而非型別阻擋
- 若未來真的要做遊戲執行期的分支播放,`convergesTo` 需要被解讀成實際的跳轉;屆時可能要重新
  評估是否升級為 DAG。這份 ADR 屆時會被 supersede

**中立**

- 需要在 P2 就提供 `level lint`,檢查孤兒節點、`order` 衝突、指向不存在 Node 的 `convergesTo`
