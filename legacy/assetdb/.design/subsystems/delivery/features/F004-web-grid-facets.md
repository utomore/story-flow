# F004: 前端網格與 facet 側欄

> **回溯建檔**:本功能在 2026-08 導入 dev-flow 三層流程之前就已完成並通過測試,
> 本文檔是遷移到 `.design/` 時依既有程式碼與測試回溯整理的紀錄,因此沒有當初的
> TodoList 與 1-to-1 測試對照表。後續變更請走 `/enhance-design` 或 `/bugfix`。

## 功能說明

挑素材的人真正使用的介面:一個能承受六千筆縮圖的網格、一個能把六千筆收斂成幾個決策的
facet 側欄、以及看得清楚像素圖的放大檢視。

四個設計前提:

1. **虛擬化而非全量渲染。** 六千筆縮圖不可能全部掛進 DOM,只渲染可視範圍。格子是固定
   尺寸的正方形(縮圖產生時已統一成正方形畫布),高度計算不必等圖片載入;總捲動高度由
   後端回的 `total` 決定,否則捲動時列高會一直跳。
2. **依需求分頁載入。** 捲到哪裡才抓那一段,而不是一次抓完——後者會讓第一次顯示等上好幾秒。
3. **查詢狀態只有一份。** `App` 是 `Query` 的唯一擁有者,`Grid` 與 `Facets` 透過 props
   讀寫,不各自持有一份條件。
4. **側欄的資訊順序由急迫性決定。** 「我剛剛選了什麼」比「還能選什麼」更急迫,所以已選
   條件放最上面;facet 計數由後端算,而且算某個 facet 時排除該 facet 自己的條件,
   否則選了「作者 = 某人」之後那份清單只剩他一個,就改不了選擇。

## 落地位置

- `web/src/App.tsx` —— `Query` 狀態、輸入去抖、facet 與 health 取用、版面組合、索引過期提示
- `web/src/api/client.ts` —— `Query` 型別與 `emptyQuery`、query string 組裝、
  `search` / `facets` / `health` / `packs`、`thumbUrl`
- `web/src/components/Grid.tsx` —— 虛擬化、欄數量測、分頁補抓、選取與放大檢視索引、格子卡片
- `web/src/components/Facets.tsx` —— 已選條件、分組收合、分類階層重排、廠商/作者依資料合併
- `web/src/components/Lightbox.tsx` —— portal 放大檢視與鍵盤操作
- `web/src/components/Detail.tsx` —— 選中素材的欄位細節與 512px 預覽
- `web/src/api/types.ts` —— 後端產生的型別(見 F003)
- `web/vite.config.ts`、`web/package.json`、`web/tsconfig.json` —— 建置與 dev proxy

## 對外行為

- **搜尋框**:中英文皆可、支援子字串;打字後去抖 200ms 才發查詢——每個按鍵都打一次 API
  會讓六千筆的查詢排隊塞住。
- **計數列**:顯示目前結果筆數與素材庫總筆數。
- **索引過期提示**:`/api/health` 回報索引與資源表筆數不符時,畫面上出現橫幅並附修復指令
  (`assetdb index`)。
- **網格**:欄數隨容器寬度變(在 effect 裡量測而不是交給 CSS grid,因為虛擬化需要明確
  知道每列幾個);一頁請求 120 筆(約數多,cols 常見 4–8 都整除,一次涵蓋數個可視畫面)。
  各入口的分頁預設刻意不同——server 60 / 上限 500、CLI 20、store 層函式庫 50。
- **分頁補抓**:捲到未載入的區間會補抓該頁,同一頁不重複發送;放大檢視用方向鍵走到可視
  範圍之外時也會補抓,否則連按方向鍵會停在一個永遠是「載入中…」的空格上。
- **換查詢的行為**:清空舊結果(顯示上一次查詢的結果比空白更糟)、回捲到頂、關閉放大檢視
  (索引指向的是舊結果集)、以 `AbortController` 取消 in-flight 請求。
- **facet 側欄**:預設展開「分類」與「類型」,其餘收合;已選條件以可移除的 chip 呈現並可
  一次清除;分類以階層縮排呈現,子分類只顯示葉節點名稱,父分類不在結果集裡的孤兒仍會顯示;
  非分類的分組最多顯示 30 項並標示還有幾項未顯示;三個布林開關(只看已命名 / 納入參考資料 /
  納入宣傳圖)。
- **廠商與作者預設合併**:實際資料裡多數廠商與作者同名,並列兩欄近乎重複的清單是浪費。
  但這是**資料決定的**,不是寫死的:只要出現一個廠商底下有多位作者,廠商就重新變成獨立的
  篩選軸並自己冒出來。
- **縮圖**:網格用 128px、細節與放大檢視用 512px;沒有 sha 的項目不留破圖。
- **鍵盤可達**:格子有 button 語意,可用 Tab + Enter/Space 走訪與開啟;放大檢視支援
  Esc 關閉、← / → 前後筆(鍵盤事件綁在 window 上,因為使用者剛剛在點縮圖,焦點還在網格裡)。
- **放大檢視的版面**:說明放在大圖正下方——看圖與讀說明是同一個動作;以 portal 掛在
  `document.body`,因為版面容器是 `100vh` 且 `overflow:hidden` 的 grid,留在裡面的絕對
  定位元素會被裁掉。
- **開發時的路徑一致**:Vite dev server 以 proxy 把 `/api` 與 `/thumb` 轉給 8787,
  前端程式碼裡的路徑在開發與正式環境完全相同,不需要條件式 base URL。

## 驗收依據

**前端目前沒有自動化測試設施。** `web/package.json` 的 scripts 只有 `dev` / `build` /
`preview`,沒有任何測試執行器(未安裝 vitest / jest / playwright 等),`web/` 底下也沒有
測試檔案或測試設定。因此本功能**沒有對應的自動化測試案例可以引用**,驗收實際依靠三件事:

1. **編譯期型別檢查**:`npm run build` 會先跑 `tsc -b` 再 `vite build`;所有對後端 DTO 的
   取用都經過 `web/src/api/types.ts`,欄位打錯或漏處理 null 是編譯錯誤。
2. **後端側的契約保護**:`server/test/AssetDB/Server/TsTypesDriftSpec.hs`
   (「checked-in 的 types.ts 與產生器輸出一致」)保證前端編譯用的型別檔沒有與後端脫鉤;
   `server/test/AssetDB/Server/AppSpec.hs` 的
   「GET /api/health / 回傳前端契約上的五個欄位,一個不多一個不少」與分頁夾制各案例,
   從後端這一側鎖住前端依賴的回應形狀與分頁行為。
3. **人工操作驗收**:對真實素材庫(約六千筆)實際操作,確認捲動流暢度、分頁補抓、
   換查詢重置、facet 互動、放大檢視翻頁與鍵盤操作。

若日後要補自動化測試,這裡是本子系統唯一沒有測試網的區塊,應以獨立的 enhancement
處理(引入測試執行器屬於介面外的基礎設施變更)。
